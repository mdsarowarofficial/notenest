## 3. Real-Time Chat System — Socket.IO

Inspect the existing chat implementation and improve it without breaking the current authentication or messaging functionality.

### 3.1 Message Timestamps

Every message should display an accurate date and time.

Requirements:

- Display the message time in the conversation.
- Show a date separator when the date changes.
- Use friendly labels such as Today, Yesterday, or an appropriate formatted date.
- Display precise times when useful, such as `8:35 PM`.
- Group messages sent on the same date where appropriate.
- Store timestamps consistently in the database, preferably in UTC, and display them in the user's local timezone.
- Ensure timestamps remain correct after refreshing, reopening a conversation, or loading older messages.
- Handle pagination and message ordering correctly.

Do not rely exclusively on the frontend clock to establish authoritative message timestamps.

### 3.2 Real-Time Messaging

Use Socket.IO if it is already present or is appropriate for the current architecture.

Implement or verify:

- Real-time message delivery.
- Authenticated socket connections.
- Authorization for conversation access.
- Correct conversation-room membership.
- Message persistence before acknowledging successful delivery.
- Reliable message ordering.
- Reconnection handling.
- Duplicate-message prevention where appropriate.
- Online/offline status and last-seen information, if appropriate.
- Unread message counts.
- Read receipts and delivery status if they fit the existing design.
- Secure handling of socket events and payload validation.

A client must never be able to join an arbitrary conversation room or read another user's messages simply by supplying a conversation ID.

Avoid unnecessary socket listeners, duplicated events, memory leaks, and multiple event handlers after reconnection.

If the application uses multiple backend instances, evaluate whether a compatible Socket.IO adapter and shared infrastructure are required.

### 3.3 Chat List Management

The chat list should be easy to manage.

Implement the following behaviors:

- Allow users to remove a conversation from their own chat list.
- Support a press-and-hold gesture on mobile, or an appropriate context menu on desktop, to reveal conversation actions.
- Provide a confirmation dialog before permanent deletion or destructive actions.
- Provide a clear option to remove a conversation from the list without affecting the other participant.
- Allow users to reopen or access conversations according to the application's conversation-request and history-retention rules.
- Update the UI immediately when appropriate, while correctly handling server failures and rollback.

Distinguish carefully between:

1. Hiding or removing a conversation from the current user's list.
2. Deleting messages for the current user only.
3. Deleting a conversation or messages for all participants.

Do not implement global deletion when the user only intends to remove a conversation from their own chat list.

Use the safest behavior consistent with the existing data model. Do not permanently delete shared conversation history unless that behavior is explicitly intended and authorized.

## 4. Email-Based User Search and Message Requests

The current user experience must prevent strangers from immediately sending unrestricted messages to anyone simply because they know that person's email address.

### 4.1 User Search

Allow users to find other registered users by email.

Requirements:

- Validate email format.
- Normalize email addresses consistently.
- Use indexed queries rather than loading every user.
- Return only the minimum information needed to identify the intended recipient.
- Never expose passwords, password hashes, OTPs, tokens, private profile information, or other sensitive fields.
- Apply appropriate authentication, authorization, and rate limits to search.
- Prevent email enumeration and abuse through carefully designed responses and throttling.

Use the existing product's privacy rules to decide what information can be shown before a connection is accepted.

### 4.2 Message Request Workflow

Implement a proper message-request system.

Expected workflow:

1. User A searches for User B using their email.
2. User A sends a message or connection request.
3. The request is stored persistently in the database.
4. User B receives an appropriate notification.
5. User B can accept or decline the request.
6. Before acceptance, User A cannot initiate unrestricted conversations or continue sending unrestricted messages.
7. After acceptance, both users can access their conversation and exchange messages according to the application's messaging rules.
8. Declined requests cannot be abused to repeatedly contact the recipient.
9. Duplicate requests and simultaneous requests must be handled safely.
10. Blocked users must not bypass the restriction by creating a new conversation.

Design clear states such as pending, accepted, declined, and blocked where applicable.

Prevent unauthorized state transitions and concurrent duplicate requests through appropriate backend validation and database constraints.

The recipient should have a straightforward way to manage pending requests.

Do not trust frontend checks alone. Enforce every permission on the server.

- Assigning courses to a semester.
- Filtering courses by semester.
- Searching for a course.

## 6. Database Architecture, Integrity, and Performance

Audit the entire database architecture before changing it.

Do not assume that the current database is inefficient simply because it may need improvement. Measure and inspect its actual behavior.

Review:

- Data models and relationships.
- Primary and foreign keys.
- Unique constraints.
- Indexes.
- Query patterns.
- Transactions.
- Connection pooling.
- Pagination.
- N+1 query problems.
- Duplicate records.
- Referential integrity.
- Soft deletion and retention rules.
- Existing migrations and rollback options.

Pay special attention to users, semesters, courses, notes, attachments, chat conversations, participants, messages, message requests, notifications, and to-do tasks.

### Database requirements

1. Use the existing database and ORM unless a change is justified.
2. Preserve all existing user data.
3. Add indexes for demonstrated or expected high-frequency query patterns.
4. Use unique constraints to prevent duplicate records where required.
5. Use transactions for operations that must succeed or fail together.
6. Use pagination for large message histories and resource lists.
7. Avoid fetching unnecessary columns and entire tables.
8. Avoid duplicate queries and unnecessary database round trips.
9. Ensure deletion and archival rules do not leave orphaned records.
10. Use safe, versioned migrations.
11. Verify migration compatibility with the current deployment environment.
12. Document any migration that could affect existing data.

Do not drop tables, delete columns, reset the production database, or wipe user data as a shortcut.

If a migration could cause data loss or require downtime, stop before executing the destructive step and explain the risk and required approval.

Where relevant, evaluate query plans and realistic data volumes instead of making unsupported performance claims.

Audit the current authentication system.

If protection is missing or insufficient, implement an appropriate solution compatible with the existing backend.

Consider:

- Login attempt throttling.
- Per-IP and per-account limits.
- Brute-force protection.
- Temporary cooldowns.
- Secure password hashing.
- Password policy and validation.
- Session or token expiration.
- Secure logout and session invalidation.
- Protection against account enumeration.
- CSRF protection where applicable.

## 8. Forgot Password and OTP Workflow

Inspect the existing forgot-password implementation.

If incomplete or insecure, implement a complete password-reset workflow suitable for the current authentication architecture.

Expected workflow:

1. User selects Forgot Password.
2. User submits their registered email address.
3. The server returns a privacy-safe response.
4. A short-lived verification code or secure reset link is sent through the configured delivery provider.
5. The user verifies the code or opens the reset link.
6. The server validates expiry, purpose, attempt limits, and single-use status.
7. The user sets a new password.
8. The reset credential becomes invalid after successful use.
9. Existing sessions are invalidated or handled according to the application's security policy.
10. The user receives confirmation and can log in securely.

If OTP is used:

- Generate codes securely.
- Set a short expiry.
- Limit verification attempts.
- Limit resend frequency.
- Invalidate previous codes when appropriate.
- Prevent replay and reuse.
- Store verification data securely, preferably using a suitable hash.
- Bind the verification process to the intended account and purpose.
- Ensure only one successful reset can occur for a given valid code.
- Do not reveal the OTP in application logs or API responses.

Use an existing configured email provider if available. Do not invent credentials or silently pretend email delivery works when it has not been configured.

Provide clear setup instructions if a required email service or environment variable is missing.

Test expired codes, invalid codes, repeated attempts, resend behavior, and successful password reset.

- Overdue tasks.
